3. Conceitos de Go que aparecem o tempo todo

Interfaces implícitas com asserção em tempo de compilação. O padrão var _ component.Config = (*Config)(nil) aparece por todo lado. É o idioma Go para garantir que um tipo satisfaz uma interface sem custo em runtime.

Factory + functional options. É o coração do projeto. Cada componente expõe func NewFactory() processor.Factory que chama algo como xprocessor.NewFactory(metadata.Type, createDefaultConfig, xprocessor.WithTraces(...), xprocessor.WithMetrics(...)). Os helpers (processorhelper.NewTraces, exporterhelper.NewLogs, scraper.NewMetrics) recebem uma função de processamento e uma lista variádica de opções (WithStart, WithShutdown, WithCapabilities). Se você entender bem esse padrão, entendeu 70% do repositório.

O prefixo x significa experimental. xreceiver, xprocessor, xexporter, xconsumer, xconfmap, xprocessorhelper. É onde vivem APIs ainda instáveis — hoje principalmente o sinal de profiles. Repare que xprocessor.NewFactory devolve um processor.Factory, e o teste faz factory.(xprocessor.Factory) para acessar CreateProfiles. Type assertion para "capability discovery" é um padrão recorrente.

context.Context como primeiro parâmetro em tudo: Start(ctx, host), Shutdown(ctx), ConsumeTraces(ctx, td), scrape(ctx). O linter revive reforça isso (context-as-argument).

Tratamento de erros. Use errors.New / fmt.Errorf com %w, erros sentinela declarados no topo do arquivo (var errClientNotInit = errors.New(...)), e go.uber.org/multierr para acumular erros (multierr.Append). O depguard proíbe explicitamente github.com/pkg/errors e hashicorp/go-multierror. O linter errorlint obriga uso correto de errors.Is/As.

Concorrência. O httpcheckreceiver é um bom estudo de caso: dispara uma goroutine por alvo com sync.WaitGroup, protege a escrita das métricas com sync.Mutex, e usa atomic.Int64 do pacote sync/atomic (o go.uber.org/atomic é proibido pelo depguard) para os callbacks de httptrace. O sharedcomponent usa sync.Once para garantir start/shutdown únicos.

Generics. O OTTL (pkg/ottl, 396 arquivos) é a parte mais "avançada" em Go do repositório. Toda a API é parametrizada pelo contexto de transformação: type ExprFunc[K any] func(ctx context.Context, tCtx K) (any, error), Getter[K any], Setter[K any], GetSetter[K any], mais os "standard" structs que adaptam funções para interfaces (StandardGetSetter[K]). Se você vai mexer em transformprocessor, filterprocessor ou routingconnector, precisa estar confortável com type parameters.

Type switches e reflexão sobre tipos dinâmicos. Como OTTL e pdata trabalham com any, switch v := val.(type) é onipresente. O linter exhaustive está configurado em modo explícito (só valida switches marcados com //exhaustive:enforce).

Struct tags mapstructure. A configuração é desserializada via confmap, então cada campo do Config leva mapstructure:"nome_no_yaml". Note também o truque _ struct{} como último campo do struct — impede inicialização por literal não-nomeado.

Testes table-driven com testify. require (aborta) e assert (continua), t.Run para subtests, e helpers de teste do core: consumertest.NewNop(), componenttest.CheckConfigStruct, processortest.NewNopSettings, confmaptest.LoadConf. Para dados de telemetria existe o pkg/golden + pkg/pdatatest (comparação com arquivos golden em testdata/).

Logging estruturado com go.uber.org/zap: logger.Error("msg", zap.String("endpoint", e), zap.Error(err)). Nunca fmt.Println.
