# Day 14: do zero ao hero, doando um componente

Objetivo do dia: o caminho completo, da ideia até o componente vivendo no
contrib. Este dia é processo, não código. O código você já escreveu nos dias
07 a 12.

## Antes de tudo: você provavelmente não precisa doar

O Collector é plugável. Você pode escrever seu componente, publicá-lo no seu
repositório como um módulo Go, adicioná-lo ao registry do OpenTelemetry e usá-lo
com o OCB. Ele funciona igual a qualquer componente do contrib.

O próprio guia de doação recomenda começar assim. Você ganha tempo para
desenvolver, colher feedback e demonstrar uso real. E uso real é exatamente o
argumento que faz alguém aceitar ser seu sponsor depois.

Doar faz sentido quando o componente interessa a muita gente, quando você quer
que ele venha na distribuição contrib e quando você tem gente disposta a mantê-lo
por anos.

## O caminho

### 1. Pesquise

Procure no registry se já existe algo parecido. Pergunte no canal
#otel-collector do Slack da CNCF. Se existe implementação concorrente, converse
com quem mantém antes de propor uma terceira.

### 2. Construa fora do contrib

Módulo Go próprio, com a estrutura dos dias 07 a 11. Use o OCB com replace para
testar dentro de um Collector real, como no day05.

### 3. Publique e colete uso

Publique como módulo Go, com tag de versão. Adicione ao registry. Deixe as
pessoas usarem. Faça release sempre que houver mudança quebrando nas suas
dependências.

### 4. Encontre um sponsor

Esta é a etapa que trava. Um sponsor é um approver ou maintainer do repositório
que se torna o revisor oficial do seu componente. Requisitos:

* Precisa ser de uma empresa diferente da sua.
* Precisa consentir antes de você abrir a issue.
* Não há garantia de conseguir um: depende da disponibilidade das pessoas.

Onde procurar: canal #otel-collector-dev no Slack da CNCF e as reuniões do SIG
do Collector.

Você também precisa de no mínimo três codeowners, sendo um deles approver ou
maintainer, que pode ser o próprio sponsor. A recomendação é que não trabalhem
todos na mesma empresa.

### 5. Abra a issue de doação

Use o template Component donation. A issue precisa trazer:

* O handle do sponsor, já com consentimento dele.
* Os handles dos codeowners, no mínimo três.
* A lista de componentes que cobrem casos parecidos, dentro ou fora do repo.
* A justificativa: motivação, casos de uso, sinais suportados.
* As opções de configuração que o componente vai aceitar.

Sem sponsor aceito, os passos seguintes não saem do lugar.

### 6. Prepare o componente para o repositório

Depois que a doação é aceita:

```bash
mkdir -p exporter/meuexporter && cd exporter/meuexporter
go mod init github.com/open-telemetry/opentelemetry-collector-contrib/exporter/meuexporter
```

Convenção de nome: pasta no formato exporter/<nome>exporter, e o type no
metadata.yaml sem o sufixo.

Makefile de uma linha:

```
include ../../Makefile.Common
```

O metadata.yaml deste diretório é um exemplo mínimo completo, com comentários.

E o doc.go com a diretiva de geração:

```go
// Copyright The OpenTelemetry Authors
// SPDX-License-Identifier: Apache-2.0

//go:generate make mdatagen

// Package meuexporter faz tal coisa.
package meuexporter // import "github.com/open-telemetry/opentelemetry-collector-contrib/exporter/meuexporter"
```

O README começa só com o marcador de seção gerada:

```
# Meu Exporter
<!-- status autogenerated section -->
<!-- end autogenerated section -->
```

### 7. Rode a bateria de geração

Da raiz do repositório:

```bash
make generate
make crosslink
make gotidy
make generate-gh-issue-templates
make gencodeowners
make addlicense
```

Existem mais alvos que o guia de doação lista (checkdoc, checkmetadata,
checkapi, goporto, tidylist, genotelcontribcol, multimod-verify). Rode todos
antes do PR, porque o CI roda e falha se o git ficar sujo.

### 8. Divida em três PRs

O projeto pede a doação em partes, e isso não é burocracia: PR grande não é
revisado direito.

PR 1, a estrutura. README, configuração e factory, normalmente usando os
helpers. Estabilidade em development. É trivial de revisar, então o limite de
tamanho não se aplica a ele.

PR 2, a implementação. Se ficar grande demais, divida em mais PRs.

PR 3, a promoção para alpha. Atualiza o metadata.yaml marcando alpha e
adicionando contrib às distributions, e inclui o componente no
cmd/otelcontribcol/builder-config.yaml.

Cada PR com sua entrada de changelog. O primeiro é change_type new_component.

### 9. Depois do merge

Você agora é code owner. Isso significa triagem de issues, revisão de PRs no seu
componente e atualização quando o core mexer nas interfaces instáveis.

Se ficar sem manutenção, o componente é marcado unmaintained e sai da
distribuição padrão. Se quebrar o build ou os testes, é removido.

Se você não puder mais manter, avise. Existe o status de emeritus, e é bem
melhor sair explicitamente do que sumir.

## Checklist de PR

Antes de pedir revisão:

```bash
cd exporter/meuexporter
make lint
make test
make generate
cd ../..
git diff --exit-code
```

E confira:

* Título no formato [exporter/meuexporter] descrição curta.
* Entrada de changelog criada com make chlog-new e validada.
* Cobertura de teste em torno de 80 por cento, incluindo os caminhos de erro.
* README documentando toda opção de configuração.
* Nenhum arquivo gerado editado à mão.
* Segredos usando configopaque.String.
* Descrição do PR escrita por você.
