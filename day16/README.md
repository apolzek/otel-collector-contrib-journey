# Day 16: mdatagen e a telemetria do seu componente

Objetivo do dia: parar de escrever à mão o que o projeto gera. O mdatagen
transforma o metadata.yaml em código, testes e documentação, e é obrigatório em
todo componente do contrib.

O componente deste dia se chama queuewatch. É um receiver de scrape que reporta
a profundidade de filas. Código em queuewatchreceiver/.

```bash
cd queuewatchreceiver
go test ./...
```

## O que o mdatagen gera

A partir de um único metadata.yaml, ele produziu neste diretório:

| arquivo | conteúdo |
|---|---|
| internal/metadata/generated_status.go | o Type e o nível de estabilidade por sinal |
| internal/metadata/generated_config.go | a config de ligar e desligar cada métrica e resource attribute |
| internal/metadata/generated_metrics.go | o MetricsBuilder, com um método Record por métrica |
| internal/metadata/generated_resource.go | o ResourceBuilder, com um setter por resource attribute |
| internal/metadata/generated_telemetry.go | o TelemetryBuilder, a telemetria interna do componente |
| internal/metadatatest/ | helpers para asserir a telemetria interna nos testes |
| generated_component_test.go | teste de ciclo de vida, criado a partir de tests.config |
| generated_package_test.go | o goleak do pacote |
| documentation.md | a documentação das métricas |
| README.md | a seção de status, entre os marcadores autogenerated |

Isso é muito código que você não escreve, não revisa e não mantém. Em troca,
você mantém um YAML.

## Rodando

No contrib basta:

```bash
cd receiver/meureceiver
make generate
```

Fora do monorepo o mdatagen não pode ser instalado com go install, porque o
go.mod dele tem diretivas replace. Compile a partir do fonte:

```bash
git clone --depth 1 --branch v0.159.0 https://github.com/open-telemetry/opentelemetry-collector.git
cd opentelemetry-collector/cmd/mdatagen && go build -o /tmp/mdatagen .
```

E rode dentro do diretório do componente:

```bash
/tmp/mdatagen metadata.yaml
```

Ele exige pelo menos um arquivo Go no pacote, então crie o doc.go antes:

```go
//go:generate mdatagen metadata.yaml

// Package queuewatchreceiver reporta a profundidade de filas como métricas.
package queuewatchreceiver
```

## As seções do metadata.yaml

Abra queuewatchreceiver/metadata.yaml junto com esta lista.

status traz classe, estabilidade por sinal, distribuições e codeowners. É o que
vira o cabeçalho do README e o generated_status.go.

resource_attributes declara atributos do Resource. Cada um vira um setter no
ResourceBuilder e um campo de configuração que o usuário pode desligar.

attributes declara atributos de métrica, uma vez, para serem referenciados por
várias métricas.

metrics declara o que o componente emite: tipo (sum ou gauge), unidade,
temporalidade, atributos e se vem ligada por padrão. Cada métrica vira um método
RecordXxxDataPoint.

telemetry declara a telemetria interna do componente, que é outra coisa: são as
métricas sobre o próprio componente, do tipo otelcol_*, que aparecem junto com
as do Collector. Não confunda com o que o componente coleta.

tests.config é a configuração usada pelo teste de ciclo de vida gerado. Ela
precisa ser válida, senão o teste falha.

## Duas regras que o mdatagen cobra na hora

As chaves de metrics precisam estar em ordem alfabética. Se não estiverem, ele
recusa com a mensagem keys are not sorted. Não é frescura: mantém o diff limpo
quando alguém acrescenta uma métrica.

Toda métrica de telemetria interna precisa de stability. É um campo escalar,
como alpha, não um bloco.

## Como o código gerado é usado

A Config combina três blocos, e só o terceiro é seu:

```go
type Config struct {
    scraperhelper.ControllerConfig `mapstructure:",squash"`
    metadata.MetricsBuilderConfig  `mapstructure:",squash"`

    Queues []string `mapstructure:"queues"`
}
```

O usuário ganha de graça collection_interval, initial_delay, timeout e a árvore
de metrics e resource_attributes para ligar e desligar cada item.

A coleta usa o builder:

```go
s.mb.RecordQueuewatchQueueDepthDataPoint(agora, valor, fila)

rb := s.mb.NewResourceBuilder()
rb.SetQueuewatchHost("localhost")
s.mb.EmitForResource(metadata.WithResource(rb.Emit()))
return s.mb.Emit(), nil
```

Detalhe importante que o teste comprova: chamar Record de uma métrica que o
usuário desligou não faz nada. Você não precisa de if em volta de cada
chamada, o código gerado já cuida.

A factory também deixa de ter constantes escritas à mão:

```go
return receiver.NewFactory(
    metadata.Type,
    createDefaultConfig,
    receiver.WithMetrics(createMetrics, metadata.MetricsStability),
)
```

Mudar a estabilidade no YAML e regerar muda o código e a documentação de uma
vez, sem chance de ficarem inconsistentes.

## Testando a telemetria interna

O pacote metadatatest, também gerado, dá o caminho completo:

```go
tt := componenttest.NewTelemetry()
s, _ := newScraper(cfg, metadatatest.NewSettings(tt))
_, _ = s.scrape(context.Background())

metadatatest.AssertEqualQueuewatchScrapeErrors(t, tt,
    []metricdata.DataPoint[int64]{{Value: 1}},
    metricdatatest.IgnoreTimestamp())
```

## O scraper, de quebra

Este componente também mostra o pacote scraper do core, mencionado no day08. A
sua função scrape não sabe nada sobre ticker, goroutine ou encerramento:

```go
sc, _ := scraper.NewMetrics(s.scrape)
return scraperhelper.NewMetricsController(
    &rCfg.ControllerConfig, set, next,
    scraperhelper.AddScraper(metadata.Type, sc),
)
```

Compare com o day08, onde o loop foi escrito à mão. Para receiver de polling,
esta é a forma correta.

## Regra de ouro

Arquivo com generated_ no nome, mais o documentation.md e a seção entre os
marcadores autogenerated do README, saem de make generate. Editar à mão é
rejeitado na revisão, e o CI detecta porque roda o generate e falha se o git
ficar sujo.
